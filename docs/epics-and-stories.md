# BioViva - Epics and User Stories

## 1. Overview & Execution Strategy

### Sprint Breakdown Approach
The BioViva project will be delivered in 5 sprints, each 2 weeks duration, aligned with the 5 bounded contexts. Sprint planning will follow these guidelines:

| Sprint | Focus Area | Primary Deliverable |
|--------|---|---|
| **Sprint 1** | Auth & Identity | User registration, login, JWT auth, RBAC middleware |
| **Sprint 2** | Product Catalog | Domain models, product CRUD, filtering endpoints |
| **Sprint 3** | Sales & Orders | Cart aggregate, order state machine, checkout, order API |
| **Sprint 4** | Inventory & Batch | Batch models, stock reservation logic |
| **Sprint 5** | DevOps & Integration | Cargo workspace, Docker Compose, multi-schema migrations |

### Story Sizing Convention
- **Story Points**: Fibonacci sequence (1, 2, 3, 5, 8, 13)
- **T-Shirt sizes** for high-level epics: XS, S, M, L, XL
- **Velocity target**: 20-25 story points per 2-week sprint (4 developers)
- **Relative estimation**: Stories compared against baseline "medium-complexity" story

### Definition of Done (DoD)
A story is considered complete only when ALL of the following are satisfied:

- [ ] Code written and reviewed per team coding standards
- [ ] Unit tests written (minimum 80% coverage for modified functions)
- [ ] Integration tests passing against PostgreSQL (single-instance, multi-schema)
- [ ] SQLx migrations written and applied (schema-aware: `auth`, `catalog`, `sales`, `inventory`)
- [ ] Code review completed (at least 2 approvals from different team members)
- [ ] Documentation updated (API specs, database schema, or user-facing docs)
- [ ] Feature demonstrated to Product Owner in staging environment
- [ ] Performance criteria met (see NFR targets per story)
- [ ] Security review passed for auth/crypto-related stories
